# Checkov compatibility candidate

This document describes the local 1.0.2 maintenance candidate. It is not a
publication or a claim that arbitrary Checkov versions are supported.

Native IaC-Guard-V properties remain scanner-independent. Scanner-backed
verification distinguishes adapter conformance from policy authority. A scanner
that emits parseable JSON is not automatically authoritative.

## Explicit version and property profiles

The candidate enumerates the 31 released versions 3.3.0 through 3.3.30 in
`src/iac_guard_v/adapters/checkov_profiles.json`. Future versions, including
3.3.31 and 3.4.0, do not enter this set automatically. Each entry pins the published
Checkov source inventory and console-script body as well as its property set.

`CHECKOV_3_3_REVIEWED_PATHS_V1` has these property variants:

| Versions | Newly qualified property surface |
| --- | --- |
| 3.3.1–3.3.7 | Common properties below, plus manifest CKV_K8S_40 with the original semantics |
| 3.3.8–3.3.30 | Common properties below; CKV_K8S_40 excluded |
| 3.3.0 | Existing released authority/scope retained; the common corpus is also replayed |

The common candidate properties are Terraform CKV_AWS_3, 18, 19, 23, 24, 53, 54,
CKV2_AWS_6, and Kubernetes-manifest CKV_K8S_10, 11, 12, 13, 14, 15, 20, 21,
22, 23, 30 and CKV2_K8S_6. Kubernetes check IDs do not qualify same-ID Terraform
provider implementations. Other properties on the additional versions remain
unqualified. The generated property/version evidence records policy-definition
hashes separately from runtime observations.

CKV_K8S_40 changed at 3.3.8: a Pod with `hostUsers: false` and UID zero changes
from FAIL to PASS. The newer rule is not declared equivalent. CKV_AWS_70,
CKV_AZURE_53/190, CKV_GCP_62/63/123 also changed, and CKV_AWS_394 was added;
none enters the additional-version authority profile merely because it has a
recognizable ID.

## Shared scanner installation

A trusted image build may install Checkov once by the project's normal mechanism,
create a separate IaC-Guard-V venv with `--system-site-packages`, and prepare:

```sh
/path/to/iacgv-venv/bin/python -m iac_guard_v.external_checkov \
  --checkov /absolute/path/to/checkov \
  --destination /protected/new/launcher-directory
```

Pass the generated `checkov` launcher with `--checkov-executable`. This opt-in
contract does not change the original Checkov executable, installation, caches,
PATH or ordinary hook. No Checkov source or dependency tree is copied into the
product venv. The product's own parser dependencies may need local bytecode-free
copies at versions compatible with the exposed environment; this does not change
the scanner's dependency resolution.

The generated launcher is an IaC-Guard-V execution interface, not a general
replacement for the ordinary Checkov CLI. Product requests use absolute input
paths, explicit frameworks, a protected config, and offline arguments. External
plugins, site startup hooks, ambient user config and arbitrary import roots are
outside this profile. The ordinary scanner path remains available for other users.

The build manifest binds the actual interpreter, original launcher, Python
standard library, all live dependency/policy/data/metadata files, and matching
wheel RECORD provenance for importable installed code. The Checkov package and
console body additionally match the pinned published artifact. Missing relocated
console/doc RECORD entries and stale unused installer metadata are described by
the explicit build snapshot rather than accepted as a complete legacy install.
The original strict, bytecode-free installation contract remains intact.

Runtime-generated bytecode is excluded from the inventory only because the
controlled invocation excludes it from execution: isolated startup, disabled site
processing, a fresh private cache prefix before startup, no sourceless bytecode
loader, fixed import roots, and private HOME/TMPDIR/XDG state. `-B` alone would be
insufficient. Hidden source/data in cache directories is rejected. Each invocation
cleans only its own exclusive private directory; it never deletes global caches.

The environment and manifest must be controlled by the operator/trusted build and
remain outside candidate content. The OS, native runtime libraries and build
operator remain trusted. This does not add hostile-input isolation or protection
against a concurrent privileged writer changing a trusted installation.

## Version selection and diagnostics

pre-commit-terraform continues to own `CHECKOV_VERSION`:

| Selection | Future hook behavior |
| --- | --- |
| `false` | Native properties remain usable; scanner-backed requests explain the missing prerequisite |
| Explicit qualified version | Reuse it; permit only qualified requested properties |
| `latest` | Use the resolved version; require its explicit authority profile |
| Explicit unqualified version | Keep the selected version and fail the scanner-backed request clearly |

Selecting all baseline findings does not silently discard unqualified checks.
If the requested set contains a property outside the selected version profile,
that scanner-backed request fails with the compatibility diagnostic.

There is no silent downgrade, substitution or hidden 3.3.0 installation.
`doctor` reports installed version, profile and qualified properties.
`CHECKOV_VERSION_UNSUPPORTED_FOR_REQUESTED_PROPERTY` identifies an unknown version
or unqualified property combination and explains that native properties remain
available.

## Reproducing qualification

`tools/compatibility/qualify.py` compares ordinary and controlled execution on
benign offline fixtures, actual import paths/distributions, registered checks,
resource/graph adapter conformance, doctor, and public repair exits 0/1/3.
A Kubernetes raw graph PASS that conflicts with independent selector evidence
remains INCONCLUSIVE; the corpus preserves that negative control.
`policy_inventory.py` independently inventories the verified wheel definitions.
Matching policy bytes alone are not sufficient for promotion.

The compatibility workflow has an explicit 31-version release-required matrix and
a separate latest canary. Canary failures require review; they never update the
support set. A new version requires artifact identity, policy review, the complete
qualification and normal product release gates before intentional promotion.
